SLM Foundry — User Manual

How to take a pile of your own data and end up with a small language model that does your task, using nothing but the web console. Read the beginner sections in order; skip ahead once you have a model that works.

What SLM Foundry is

Beginner

SLM Foundry is a workshop for building your own small language model. You bring examples of the work you want done; it produces a model that does that work. Everything happens in a web console — you never write training code.

Small language model (SLM)
A language model with roughly 0.1 to 5 billion parameters, rather than the hundreds of billions in a frontier model. In plain terms: a model small enough to run on your own hardware, cheap enough to call constantly, and narrow enough that it can be genuinely excellent at one job rather than passable at everything.
Fine-tuning
Taking a model that already understands language and adjusting it on your examples so it does your specific task. In plain terms: you are not teaching it English. You are teaching it your house style, your terminology, and what a good answer looks like where you work.

Why bother, when a frontier model can already do it?

Three reasons people actually reach for this:

  • Cost and latency. A 0.5B model answering in 80 ms for a fraction of a cent behaves differently in a product than a frontier model answering in two seconds. Some features only exist at the cheap end.
  • The data cannot leave. A self-hosted small model keeps regulated or confidential material inside your perimeter.
  • Consistency. A model fine-tuned on ten thousand of your own examples will match your conventions more reliably than any prompt.
What it is not SLM Foundry does not train models from scratch, and it will not make a 0.5B model match a frontier model at open-ended reasoning. It makes a small model very good at your task.

The shape of the work

Every project follows the same arc. You will not do all of it on day one — stages 1 and 2 alone are often enough. 

1. Data        upload examples of the task
2. Fine-tune   teach the base model from those examples          (SFT)
3. Feedback    show people pairs of answers, ask which is better
4. Align       train on those preferences               (DPO / PPO / GRPO / GSPO)
5. Benchmark   score the result on data it has never seen
6. Promote     mark a version as production
        ↑                                                     │
        └───────────── next round of feedback ────────────────┘

The words you need

Beginner

Six terms cover almost everything in the console.

Dataset
A file of examples you upload. Comes in four kinds, covered later. Frozen once accepted — so a model can always say exactly what it was trained on.
Run
One training attempt: a method, a base model, some data, and settings. If it succeeds it produces a model version.
Job
A unit of background work waiting for a machine. Runs, evaluations and candidate generation are all jobs. Why this matters: closing your browser does not stop anything. Work happens on shared workers, not in your tab.
Model version
A trained artifact with a version number, its scores, and a record of what produced it. Versions are numbered per name, so support-bot v1, v2, v3.
Review batch
A campaign that samples prompts, generates candidate answers, and puts them in front of people to compare. This is how opinions become training data.
Preference pair
One prompt with a better answer and a worse answer. The universal currency here — every alignment method consumes exactly this.

Your first fine-tune

Beginner

Start with supervised fine-tuning on demonstrations. It is the foundation: every other method assumes a model that is already competent, and improves it.

  1. Prepare your examples Make a .jsonl file — one JSON object per line — where each line is a question and the answer you wish the model had given. 
    {"prompt": "What's the policy on expense reimbursement?",
 "completion": "Receipts are required above $25, filed within 60 days."}
{"prompt": "How does parental leave work?",
 "completion": "Sixteen weeks at full pay, any time in the first year."}

    How many do you need? Around 50 will show you something. 500–2,000 is where a narrow task starts working properly. More helps, but variety helps more than volume — a hundred genuinely different questions beat a thousand rephrasings of ten.

  2. Upload it Data tab → drop the file → give it a name → set Kind to sft → Upload & validate.

    Every row is checked immediately. Malformed rows are dropped and listed with their line numbers rather than failing the whole upload, so you find out here instead of forty minutes into training.

  3. Launch the run Train tab → New run → pick Supervised fine-tuning → choose a base model → select your dataset → Queue run.

    Leave every hyperparameter alone the first time. The defaults are sensible and you cannot judge a change without a baseline.

  4. Watch it Click the run to open its panel: a live log, loss curves, and sample generations. You can close the browser; it keeps going.
  5. Try it Models tab → your new version → Try it. Tick compare against the base model to see the same model with your training switched off, side by side. That comparison is the honest one: nothing differs except the fine-tune.
The one thing to get right Your examples define the target. If they are inconsistent — two answers to the same question in different styles — the model learns to be inconsistent. Time spent making demonstrations uniform pays back more than any hyperparameter.

Reading your results

Beginner

The run panel shows numbers that fall into three groups.

MetricWhat it meansWhat you want
loss How surprised the model was by the correct answer. Falling, then flattening.
val_loss The same, on examples held back from training. Falling with loss. If it turns upward while loss keeps falling, the model is memorising — stop and use fewer epochs.
val_token_acc How often it would have picked the exact next word. Rising. Low is not fatal — there are many good phrasings.
grad_norm The size of each update. Steady. Wild spikes mean the learning rate is too high.

Numbers are not the point — read the samples

Every run captures generations on held-out prompts. A run whose loss fell beautifully while its outputs got worse is a real and common event, and the samples are the only place you will see it. Read them first.

The amber “tiny backend” tag

If a run is tagged tiny backend, the base model you asked for was not available on the machine, so training ran against a randomly-initialised stand-in.

The training itself was completely real — the same mathematics, the same code path. But the model started from noise, so the quality numbers mean nothing and the generations will be gibberish. It is there so you can exercise the whole pipeline before committing hardware. Download the base model, or set the backend explicitly, to get real results.

The four kinds of data

Intermediate

Each kind answers a different question, and each method demands a particular kind. Upload JSONL (one object per line) or a JSON array.

sft — demonstrations

“Here is a good answer.” Used by supervised fine-tuning. Three accepted shapes:

{"prompt": "…", "completion": "…"}

{"messages": [{"role":"user","content":"…"},
              {"role":"assistant","content":"…"}]}

{"messages": [{"role":"system","content":"…"},
              {"role":"user","content":"…"}],
 "completion": "…"}

preference — comparisons

“This answer beats that one.” Used by DPO and by reward models.

{"prompt": "…", "chosen": "…", "rejected": "…", "margin": 0.8}

margin is optional, between 0 and 1: how much better the chosen answer is. A landslide gets 1.0, a close call gets 0.3, and the training loss weights the pair accordingly. You usually do not write these by hand — the review console produces them.

prompts — questions without answers

“Here are the things people ask.” Used by every reinforcement-learning method (which generates its own answers and scores them) and by review batches. 

{"prompt": "…", "meta": {"topic": "…"}}

benchmark — the exam

“Here is how we will judge it.” Never trained on. Whatever fields you supply determine how it is scored:

FieldsScored by
choices + answer Accuracy. The model rates each option and the highest wins — it is not asked to write the answer out, so it cannot be marked wrong for phrasing.
reference Exact match and token F1 (word overlap with the reference).
rubric Judge score — a model grades against your rubric.
Build the benchmark first Fifty held-out examples written before you start training are worth more than any amount of tuning afterwards. Without them you have no way to tell an improvement from a change.

What validation does to your upload

  • Normalises every shape into one internal form.
  • Deduplicates identical rows silently and reports the count — this is why 140 uploaded rows may become 121.
  • Drops malformed rows with line numbers and reasons.
  • Freezes the file. Corrections upload as a new version.

Teaching by comparison

Intermediate

Demonstrations have a ceiling. Writing the ideal answer to every question is expensive, and for questions of tone or judgement there is no single right answer to write. Comparison is cheaper and often more informative: people are far better at picking the better of two answers than at producing the best one.

Running a batch

  1. Create it Review → Batches → New batch. Pick a prompts dataset and the model to sample from.
  2. Candidates are generated The model answers each prompt several times at temperature 1.0 — deliberately varied, because two near-identical answers give a reviewer nothing to choose between.
  3. People review Review → Review queue. Keyboard driven: 1/2 to pick, T for a tie, B for both bad, S to skip, Enter to submit.
  4. Assemble the pairs Batches → Build pairs turns the verdicts into preference pairs.

Settings that matter

SettingWhat it does
Candidates per prompt 2 is the standard A/B. More produces more pairs per prompt but takes longer to judge.
Reviewers per item 1 is fastest. 2+ lets the system measure agreement and weight contested items lower. Use ≥2 for anything you will act on.
AI pre-labelling 0 = humans only. Above 0, a judge model also labels that fraction, and the overlap measures the judge against your people. At 1.0 every item gets an AI opinion.

Why the console behaves the way it does

  • Ties are a real answer. Forcing a preference between two equally good answers manufactures a label that looks exactly like a real one. Ties are recorded and then excluded.
  • The AI's answer stays collapsed. A reviewer who reads it first is confirming it, not judging — and the whole point of the overlap is to measure the judge independently.
  • Answer order is shuffled per reviewer, so two people do not share the same position bias.
  • “Sampling p” is shown to you because the queue deliberately favours informative items. Recording the probability is what lets a win-rate measured on reviewed items say anything about the ones nobody reviewed.
  • Disagreement escalates. When reviewers split badly the item goes to a lead under Adjudicate rather than being settled by majority-of-two.
How many pairs? A few hundred will move a small model. One to five thousand is a solid round. Quality dominates: 500 pairs your team agrees on beat 5,000 collected in a hurry, because inconsistent preferences teach the model that the distinction does not matter.

Training on preferences

Intermediate

With pairs in hand, use DPO. It is the most reliable way to spend preference data: no reward model to train, no sampling loop, and far less that can quietly go wrong than the reinforcement-learning methods.

  1. Train → New run → DPO
  2. Leave “Training data” empty to use the pairs collected in the review console, or select an uploaded preference dataset.
  3. Set “Start from” to your SFT model. This is the step people miss. DPO improves an existing policy; pointed at a raw base model it has far less to work with.
  4. Attach your benchmark so the finished model is scored automatically.

What to watch

MetricReading
reward_acc How often the model now prefers what your reviewers preferred, on training data. Climbs quickly; pinning at 1.0 means the gradient is spent and more epochs only overfit.
heldout_pref_acc The number that matters. The same thing on pairs it never trained on. Above 0.5 means it generalised.
logp_chosen The trap. DPO only constrains the difference between the two answers, so it will happily make the good answer less likely as long as it makes the bad one less likely faster. If this falls steadily, raise beta or set an auxiliary SFT weight.
implicit_kl How far the model has drifted from where it started. Large values with flat accuracy means it is wandering, not learning.
If DPO destabilises Lower the learning rate first — DPO wants roughly an order of magnitude less than SFT. Then raise beta from 0.1 toward 0.3 to keep the model closer to its starting point. If your labels are noisy, set label_smoothing to 0.1.

Benchmarking and promoting

Intermediate

Scoring a model

Attach a benchmark to a run and it is scored automatically when training finishes. Otherwise: Models → the version → Run evaluation. The Leaderboard ranks every model scored on one benchmark — deliberately one at a time, because ranking models by scores from different datasets is the most common way a registry misleads the people reading it.

Watch degenerate_rate The share of answers that collapsed into repetition or never stopped. Both are common fine-tuning failures that leave the headline metric looking unremarkable rather than obviously broken.

The lifecycle

draft ──▶ evaluated ──▶ staging ──▶ production
                                        │
                       (next promotion) ▼
                                     archived
  • draft — trained, never scored. Cannot go to production.
  • evaluated — has a benchmark score.
  • staging — a candidate.
  • production — one per name at a time. Promoting a new version archives the incumbent in the same transaction.

Promotion requires the lead role, copies the artifact to a directory that is never written again, and is recorded in a tamper-evident audit log. Lineage on each model walks the chain back — DPO → SFT → base — so “what produced this?” is a question with an answer.

Teams, roles and the queue

Intermediate

Roles

RoleCan do
viewerRead everything in their team.
member+ upload data, launch and cancel runs.
reviewer+ annotate in the review queue.
lead+ adjudicate disagreements, promote models.
admin+ manage teams, quotas and users.

Everything is scoped to your team. Another team's datasets, runs and models are invisible; only their job counts show on the Queue tab, so you can see the cluster is busy without seeing what it is busy with.

How work gets scheduled

Jobs run on shared workers. Scheduling is fair-share, not first-come: candidates are ordered by how many jobs your team already has running before priority is considered. A team that queues 400 jobs overnight cannot monopolise the cluster, and a team with nothing running always gets the next free worker.

Cancelling is cooperative — the trainer stops at the next step boundary rather than being killed mid-update, which would leave a corrupt checkpoint. Expect a few seconds.

“No live workers” If the Queue tab says this, jobs will pile up and never start. Someone needs to run python -m foundry.worker. Nothing is lost — queued work begins as soon as a worker appears.

Choosing an alignment method

Advanced

Five methods can consume preference signal. They are not interchangeable, and the differences are practical rather than theoretical. The Methods manual covers the mathematics; this is how to pick.

MethodNeedsReach for it whenCost
DPO preference pairs Default. You have pairs and want them spent reliably. Lowest — one pass per pair, no sampling.
GRPO prompts + a reward signal You can score an answer but have no pairs — a checkable answer, a test suite, a judge. High — G samples per prompt per step.
GSPO prompts + a reward signal Same as GRPO, but your outputs are long (hundreds of tokens) or GRPO was unstable. Same as GRPO.
PPO prompts + a trained reward model You need maximum control and have the budget to tune it. Highest — sampling plus a critic.
RLAIF prompts + a policy You cannot get enough human labels. Replaces the labelling step, then hands the pairs to one of the above. API cost per rollout.
A sane progression SFT → collect a few hundred pairs → DPO → benchmark. Only if DPO plateaus and you have a genuine scoring function should you reach for GRPO or GSPO. PPO last, and only if you know why the others were not enough.

GRPO or GSPO?

They share everything except where the correction is applied. Reward is a whole-answer judgement, but GRPO applies a per-token correction to it, so a 500-token answer accumulates 500 independently noisy adjustments against a single score — and one freak token can dominate the update. GSPO makes one correction per answer.

  • Short outputs (under ~100 tokens), single update pass: GRPO.
  • Long outputs, or several update passes per batch: GSPO.
  • GRPO training that collapses or spikes for no visible reason: switch to GSPO before tuning anything else.
Do not copy clip ranges between them GSPO's ratios are length-normalised and sit extremely close to 1.0, so its defaults are around 0.0003 where PPO and GRPO use 0.2. That is the equivalent strictness, not a typo. Pasting 0.2 into GSPO disables clipping entirely. If the run warns that nearly every sequence is being clipped, lower the learning rate rather than widening the range.

Where reward comes from

Advanced

The RL methods need a number for each generated answer. Three sources, chosen automatically in this order:

  1. A trained reward model If you attach one. Highest fidelity to what your reviewers actually said. Weakness: it goes stale — as the policy improves it produces answers unlike anything the scorer was fitted on, and the score drifts from reality.
  2. A verifier Used automatically when at least half your prompts carry a reference answer. Word overlap plus a bonus for an exact match. Strength: free per rollout and impossible to game. Limit: only works for checkable tasks.
  3. A judge model The fallback. Never stale, costs money per rollout. Without an API key it degrades to heuristic-v1, a mechanical scorer that is labelled as such everywhere so it cannot be mistaken for a model's opinion.

Whichever is used, the run log states it on the first line. All three are normalised to roughly 0–1 before reaching the optimiser — KL coefficients and clip ranges are tuned against an assumed reward scale, so an unnormalised source would silently change the effective strength of every other setting.

Reward hacking Any learned reward model can be gamed, and a policy optimised hard enough will find how. The classic tell is length — answers growing steadily while the reward climbs. Watch completion_len next to reward, and check length_bias_corr on the reward model itself. The KL penalty is the main defence; if reward is climbing while KL explodes, the model has not improved, it has found a bug.

RLAIF and auditing the judge

Advanced

RLAIF replaces the labelling step, not the optimiser. A judge model ranks sampled candidates into preference pairs, and then DPO, GRPO or GSPO consumes them exactly as it would human pairs. This is why Optimiser is a visible setting: “we used RLAIF” says nothing about how the weights actually moved.

The three safeguards

  • Position debiasing. Judges favour whichever answer they read first. Every comparison is scored in both orders and averaged. When the two orders disagree the verdict becomes a tie rather than a coin flip, and the flip rate is reported. Above ~25% the judge is largely responding to presentation order and its labels are weak evidence.
  • A minimum margin. Pairs the judge could barely separate are discarded. A forced verdict between equivalent answers is noise with a label attached — worse than no data, because it is indistinguishable from signal.
  • A human spot-check. A fraction of judged pairs is queued for real people. Without this the judge is unfalsifiable: nothing in the system would ever disagree with it.

Reading the Agreement tab

Raw agreement is not the number to trust. On a two-way choice, two people guessing randomly agree 50% of the time, so 60% agreement looks respectable and means almost nothing. Cohen's kappa corrects for that.

KappaInterpretation
< 0.2Barely better than chance. Do not train on these labels.
0.2 – 0.4Weak. Usable with a large human spot-check.
0.4 – 0.6Moderate. Reasonable for scaling up labelling.
> 0.6Strong. The judge tracks your reviewers well.

If kappa is low, the usual cause is not a weak judge but an underspecified question. Sharpen the rubric so it grades something visible in the text.

Tuning hyperparameters

Advanced

Change one thing at a time, against a fixed benchmark. In rough order of impact:

SFT

SettingDefaultMove it when
epochs3 Down if val_loss turns upward. Up (to 5–8) for very small datasets.
learning_rate2e-4 Down 3–5× if grad_norm spikes or loss oscillates. This is a LoRA-scale rate — roughly 10× a full fine-tune.
LoRA r16 Up to 32–64 for a substantial style or domain shift. 8 is plenty for format-following.
max_seq_len1024 Long enough for your longest example — the prompt is truncated from the left, never the answer.
grad_accum1 Up when you want a larger effective batch than memory allows.

DPO

SettingDefaultMove it when
beta0.1 Up (0.2–0.5) if the model drifts or logp_chosen collapses. Down (0.05) if it barely moves.
learning_rate5e-6 Down first whenever DPO misbehaves.
loss_variantsigmoid ipo resists overfitting on small or very clean sets.
label_smoothing0 0.1–0.2 with crowd-sourced or contested labels.
sft_weight0 0.1–1.0 to stop logp_chosen falling.

GRPO / GSPO

SettingDefaultMove it when
group_size8 The baseline is the group's own mean, so below ~4 the advantage is mostly noise. Raise it if the log reports degenerate groups.
kl_coef0.04 Up if the model drifts or starts reward-hacking. Down if it will not move at all.
temperature1.0 Below ~0.8 the group collapses to identical samples and there is nothing to compare.
mu1 / 2 GRPO: 1 keeps it exactly on-policy. GSPO: >1 is where it earns its keep.
A degenerate group All G samples scored identically, so there is nothing to prefer and the update contributes zero. A few are normal. All of them means your reward source cannot distinguish the model's outputs — fix that before touching anything else.

Running it for real

Advanced

Database

SQLite is the default and is fine for one worker. Move to Postgres as soon as you run more than one: 

export FOUNDRY_DATABASE_URL=postgresql+psycopg://host/foundry

Split your workers by job kind

The single most effective operational change. Interactive work — generating candidates for a reviewer who is waiting — should never queue behind an overnight retrain. 

# GPU box: training only
python -m foundry.worker --kinds train

# small box: everything interactive
python -m foundry.worker --kinds generate,judge,eval,assemble

Environment

VariableDefaultPurpose
FOUNDRY_DATABASE_URLlocal SQLiteWhere state lives.
FOUNDRY_DATA_DIR./varUploads, artifacts, promoted models.
FOUNDRY_BACKENDauto torch fails loudly instead of falling back to the tiny model. Set this in production.
ANTHROPIC_API_KEY—Enables the real judge.

What survives a crash

A worker holds each job on a lease it must keep renewing. If it is killed, OOMs, or drops off the network, the lease expires and the job is requeued automatically — and the dead worker's late writes are rejected. You lose one job's progress, never the queue and never someone else's work.

Before exposing this publicly Passwords are hashed with PBKDF2 from the standard library — deliberate, to avoid a native dependency, and the first thing to replace with argon2id or an SSO integration. Session tokens are already stored only as hashes, so a database dump does not hand over live sessions.

Troubleshooting

Advanced
SymptomLikely cause and fix
Jobs stay queued forever No live worker. Check the Queue tab; start one.
Run failed: “no training data” No dataset attached and no preference pairs collected. Attach one, or build pairs from a review batch.
Run tagged “tiny backend” unexpectedly The base model is not present locally. Download it, or set FOUNDRY_BACKEND=torch to fail loudly instead.
Upload accepted far fewer rows than expected Deduplication. Identical rows are dropped and counted — check the dataset's statistics.
val_loss rising while loss falls Overfitting. Fewer epochs, lower LoRA rank, or more data.
logp_chosen falling during DPO Both likelihoods collapsing. Raise beta or set sft_weight to 0.1–1.0.
Reward climbing but outputs look worse Reward hacking. Check completion_len and KL; raise kl_coef.
GSPO warns nearly everything is clipped Learning rate too high for the clip range. Lower it — do not widen the range.
Every group is degenerate Reward source cannot separate the outputs, or temperature is too low.
Review queue empty but items remain You have already been assigned them all; they are waiting on other reviewers.
Cannot promote to production The version is still draft — benchmark it first. Promotion also needs the lead role.
